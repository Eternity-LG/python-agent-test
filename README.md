# agent-101

不依赖 LangChain / LangGraph，只用 `openai` SDK 手写 agent loop；然后用**真实 run 的 token 与调用数据**逐条改工具和提示词，把一次日志统计任务从 **159,553 tokens / 67 次调用** 压到 **10,359 / 5**。

这不是一个通用框架，是一个用来把"agent 的成本花在哪"量出来的实验台：每次只改一个变量，跑完看 trace，再决定下一个改动。

## 目录

| 文件 | 作用 |
|---|---|
| `agent.py` | v1：约 300 行的最小闭环。3 个工具（`list_files` / `read_file` / `calc`）、沙箱校验、错误回灌、`--self-test` 假模型自检 |
| `agent2.py` | v2：长任务版。加了 `findstr`、大结果外置、`trace.jsonl`、checkpoint 与 `--resume`、零值自证、无进展守卫 |
| `eval.py` | 6 条固定任务的自动评测。答案由 oracle 现算，打分靠 `TOTAL=` 输出契约 |
| `probe.py` | 换 provider 前的契约测试：只验 tool calling 能不能用，不产生 run 目录、不污染基线 |
| `envfile.py` | 零依赖 `.env` 加载器。**项目内 `.env` 覆盖系统环境变量**，空值与占位符不注入 |
| `BASELINE.md` | 基线记录：逐 run 对照、每次改动的因果、噪声带与判读规则 |
| `sandbox/` | 被 agent 读的数据（`batch/log_01..20.log` + 几个根目录日志），也是沙箱边界 |
| `runs/` | 运行时产物，不入库。自检单独落在 `runs/_selftest/` |

## 快速开始

```bash
pip install -r requirements.txt

# 在项目根建 .env（已 gitignore），三行就够
OPENAI_API_KEY=sk-xxx
OPENAI_BASE_URL=https://api.deepseek.com/v1
MODEL=deepseek-v4-flash

python agent.py --self-test     # 假模型跑完整循环，不花额度
python agent2.py                # 真跑，产物在 runs/<时间戳-id>/
python eval.py --limit 3        # 先跑 3 条试水，结果落 runs/eval_*.json
```

配置全部走环境变量：`OPENAI_API_KEY` / `OPENAI_BASE_URL` / `MODEL` / `RUNS`（runs 根目录）/ `AGENT_SANDBOX`。
`MODEL` 与 `BASE_URL` 在 **import 那一刻**就定值了，所以 `envfile.load_env()` 必须在 `import agent` 之前调用——这也是 `.env` 优先于系统变量的原因：IDE 里遗留的 `OPENAI_API_KEY` 静默顶掉 `.env`，表现就是"改了配置没反应"。

换模型先跑 `python probe.py`：模型名错是 404，schema 字段不认是 400，有的模型把调用塞进 `content` 返回 0 个 `tool_calls`（第一步就被判成"结束"），有的返回空串 `arguments`（`json.loads` 直接抛）。这些都不是价格问题，是契约问题。

## agent loop 只有四件事

1. **assistant 消息必须原样回填**，尤其是 `tool_calls`。少这一条，下一轮就是 `tool messages must follow tool_calls`。
2. **终止条件只有一个**：模型不再请求工具。外加 `MAX_STEPS` 硬顶（v1 是 12，v2 是 40），否则能一直循环到烧完额度。
3. **`arguments` 是 JSON 字符串**，不是 dict。模型偶尔传空串，兜底 `or "{}"`。
4. **`tool_call_id` 必须和 `call.id` 对上**，否则 400。

另外两条不加会疼的：

- **错误回灌而不是抛出**：工具失败把 `类型 + 消息` 作为 tool 结果返回，agent 才有机会自愈。
- **沙箱校验**：所有路径 `resolve()` 后必须落在 `sandbox/` 内。工具越权是 agent 最常见的安全事故。

## v2 在 v1 之上加的东西

| 机制 | 解决的现象 | 代价 / 边界 |
|---|---|---|
| `findstr` 聚合计数 | 逐文件 `read_file` 把 40k 字符塞进上下文 | 目录模式与 `list_files` 信息重叠，会多一次调用 |
| `show_lines` | 只需核对几行却要读整篇 | 输出上限收紧到 12 行（约 1100 字符），防止自己触发落盘 |
| 大结果外置 | 单次工具返回超 `ARTIFACT_THRESHOLD=1200` 就顶爆上下文 | 落盘摘要要够模型做判断；`read_artifact` 自身**不能再落盘**，否则"读→落盘→再读"死循环 |
| `read_file` 字符预算 | 只限行数时，27 行就能超 1200 → 落盘 → 再读回来，一次读原文付两次钱 | 预算 1000 是硬顶（不进 schema），必须低于 1200；因此必须配 `offset`，否则文件尾部永远读不到 |
| 零值自证 | 命中 0 时模型分不清"真没有"还是"没读到"，只能裸读全文求证 | 只在 0 命中时触发，给分母 + 大小写变体 + 可照抄参数；部分文件为 0 也补分母，超 32 个文件则只给提示 |
| 无进展守卫 | 反复换参数打转 | 结果指纹（抹掉落盘名/分页头/时间戳后取 md5 + 长度桶），连续 2 步无新指纹注入一次提示，然后归零 |
| 重复调用拦截 | 同参数死循环 | 同一 `(name, args)` 第 4 次起直接返回"结果不会变" |
| checkpoint | 进程被杀就得从头付钱 | 每步 `state.json.tmp` + `os.replace` 原子替换；`--resume` 只恢复 messages 与计数 |
| `trace.jsonl` | 事后只能看最终答案 | 每步记 ms / chars / tokens，成本分析全靠它 |

## 评测

`eval.py` 的 6 条任务覆盖四种情况：正常计数（ERROR / error / WARN）、需要工具参数（忽略大小写）、**近义词陷阱**（`WARNING` 实际 0，但 `WARN` 有 81）、**零值陷阱**（`FATAL` 不存在）。

两条纪律：

- **答案不由人手填**。`oracle()` 每次现算，改数据它自己跟着变。硬编码 37/80 的代价是：改数据后 eval 会静默地拿旧答案判分。
- **输出契约**。question 末尾要求报告最后一行写 `TOTAL=<数字>`，打分器单正则提取。此前靠自然语言匹配，正则被 markdown 粗体 `**37**` 击穿，答对了也判 FAIL；提取不到单独记 `None`，与"算错数"区分开。

判读规则（否则单次对比全是噪声）：

1. tokens 变化 < 15% 或调用变化 < 25% → 视为噪声，不归因。
2. 成本结论要重复 2 次以上且同向。
3. 机制类改动看**确定性痕迹**（artifact 数、某调用出现/消失、`ctx_chars` 精确减少），这类证据与采样无关，不用重复。
4. A/B 不要"先跑完 A 再跑 B"，存在会话级漂移；要么交错跑，要么接受偏差。

同代码两轮实测：31 ↔ 38 次调用、79.7k ↔ 89.6k tokens，即调用 ±23%、tokens ±12% 的纯噪声。

## 实测

| 改动 | 确定性效果 |
|---|---|
| 全文搬运 → `findstr` 计数 | 工具返回 40k → 6.6k 字符，调用 67 → 11 |
| 工具描述里写明优先级 | 目录聚合成为首选，调用 26 → 9 |
| `ignore_case` 参数 | t03：49 次调用 / 167,280 tokens → **4 / 9,216** |
| 零值自证覆盖"部分文件为 0" | `read_file` 消失、artifact 归零、调用 8 → 5 |
| `read_file` 字符预算 | artifact 三轮 1 → 0 → 0；**成本中性**，不宣称提速 |

成本演进（同一任务、同一模型）：

| run | 改动 | 步 | 调用 | tokens | artifact |
|---|---|---|---|---|---|
| `1117-163110-be1d` | v2 原版，`read_file` 全文 | 13 | 67 | 159,553 | 24 |
| `1117-185106-02d5` | 描述引导 + 单文件 + 阈值 1200 | 7 | 9 | 18,444 | 1 |
| `1118-151357-6137` | 零值自证覆盖单文件 0（换 MiMo） | 5 | 5 | 10,359 | 0 |

跨模型只比"步"和"调用"两列：分词器不同、思考模型的 `reasoning_content` 还会占掉 30% 上下文，tokens 不可横比。

eval 全量 6/6 通过，合计 76,224 tokens，6 条串行约 70 秒。

## 已知问题

- **每步重发全量历史**是当前最大成本项，不是工具返回。run6 最后 3 步占 63% 的 tokens。要动就得做摘要或分层记忆，属于结构性改动。
- **`reasoning_content` 未剥离**：思考模型每步都要重付一遍思考文本（run7 中 3,288 字符，占上下文 31%）。修法是一行 `pop`，但它同时污染 `ctx_chars` 指标，得单独开一轮验证。
- **`list_files` 与 `findstr` 目录模式重叠**，稳定多付 1 次调用（约 219 字符）。
- **eval 数据偏规整**：每文件行数、日志格式都太整齐，模型容易外推。已给 `log_01` 加了一行打破均匀（t02 因此涨到 A 轮最贵的 18,149 tokens），但仍需重造成长尾分布。
- **6 条串行跑**，没有并发；任务一多就慢。

## 为什么不用框架

框架把"上下文怎么涨的、钱花在哪一步、工具返回多大"藏起来了。这个项目的每一步收益都来自看得见的东西：一次工具返回多少字符、模型在第几步开始重复、哪个参数没写进 schema 导致它不用。

代价也很明确：没有现成的状态机、没有并行工具执行、没有持久化后端，所有这些都得自己写，而且只针对"读文件 + 计数 + 写报告"这一类任务。要做通用 agent，到这一步就该换成 LangGraph 了。
